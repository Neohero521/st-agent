# v1.8：酒馆安全网与磁盘管家

工具数 125 → 139（`adv-tools-v18.js`，14 个）。

这一版不是凭感觉挑的：把 `src/endpoints/` 下 **46 个模块**的路由逐个列出来，跟已有的 125 个工具做差集，剩下真正没人碰过的服务端能力只有几块——设置快照、data-maid、聊天备份、向量库、统计。它们不是"锦上添花"，恰好是 Agent 大量写操作时**最缺的两样东西：能退回，和能清理**。

## 一、设置快照：给批量写操作上保险

Agent 一旦开始批量改 `settings.json`（换主题、改采样器、写扩展设置），出错就是整份设置坏掉。

| 工具 | 端点 | 行为 |
| --- | --- | --- |
| `snap.list` | `/api/settings/get-snapshots` | 列快照：文件名、时间、体积、总量 |
| `snap.make` | `/api/settings/make-snapshot` | 立刻打一张（服务端调 `backupUserSettings(handle, false)`，返回 204 无 body） |
| `snap.load` | `/api/settings/load-snapshot` | 读快照**结构**：顶层键、字符数、是否含 characters / world_info / power_user |
| `snap.restore` | `/api/settings/restore-snapshot` | 整份覆盖 `settings.json`，需 `confirm: true` |

`snap.load` 故意不返回全文——settings.json 常有几 MB，全吐给模型既浪费上下文也没意义。看结构就够了，要看具体字段就 restore 之后用 `setting.get`。

`restore` 的实现是 `rmSync(settings.json)` + `copyFileSync(snapshot, settings.json)`，返回 204。**覆盖完页面里还是旧内存值，必须刷新**——工具返回里写了这句。

实测：

```
snap.list   → count 9，每张 45 KB，最新 settings_default-user_20261127-081605.json
snap.make   → before 9 / after 10，made settings_default-user_20261127-085449.json
snap.load   → parsed true，top_keys: firstRun, accountStorage, currentVersion, username,
              user_avatar, amount_gen, max_context, main_api, world_info_settings, …
             （含 power_user / extension_settings / oai_settings / nai_settings 等）
snap.restore 不带 confirm → 拒绝："restore 会整份覆盖当前 settings.json（不可撤销），确认就传 confirm: true"
```

## 二、data-maid：真扫磁盘的孤立文件清理

`audit.run`（v1.7）是"读内存统计"，`maid.report` 是"读磁盘清单"，两者不是一回事。

`/api/data-maid/report` 的流程是：服务端遍历用户目录 → 生成 raw report（九类孤立文件）→ **sanitize** 掉真实路径换成 SHA-256 hash → 返回 `{ report, token }`。删文件必须把 `token + hash` 一起发回去，服务端按 token 里的映射找到真实路径，再 `isPathUnderParent` 校验一次才 unlink。

九类是：`images` `files` `chats` `groupChats` `avatarThumbnails` `backgroundThumbnails` `personaThumbnails` `chatBackups` `settingsBackups`。

| 工具 | 说明 |
| --- | --- |
| `maid.report` | 按类给数量 / 体积 / 前几条样例（name + hash + kb），并回 token |
| `maid.delete` | 必须传 token + 具体 hash 数组 + `confirm: true`；token 用一次就失效 |

工具层**故意不支持"全删"**：`hashes` 必须是同一次 report 里出现过的，不在报告里的会被服务端静默忽略。这样模型没法"手滑清空磁盘"。

实测（这个测试环境其实很干净，但仍有 14 个）：

```
maid.report → total 14 / total_kb 428
              rows: images 0, files 0, chats 0, groupChats 0,
                    avatarThumbnails 0, backgroundThumbnails 0, personaThumbnails 0,
                    chatBackups + settingsBackups 共 14
maid.delete 不带 token → 拒绝："需要 token（先用 maid.report 拿，它跟这一份报告绑定）"
```

也就是说：**即使你没删过任何东西，酒馆自己也会堆出孤立文件**——主要是每次保存设置时打的 settings 快照、每次保存聊天时打的 chat 备份，这些从来不自动清。

## 三、聊天备份：酒馆自己打的 jsonl

`/api/backups/chat/get` 会把 `backups/` 下所有 `chat_*.jsonl` 交给 `getChatInfo` 逐个解析。

| 工具 | 说明 |
| --- | --- |
| `backup.chats` | 文件名、体积、楼层数、最后一条文本、时间 |
| `backup.delete` | 删单个备份（服务端校验文件名必须以 CHAT_BACKUPS_PREFIX 开头） |

第一版把字段猜成 `mes_count` / `message_count`，全 null。读源码才看到 `getChatInfo` 的真实字段是：

```
file_name / file_size（格式化字符串，如 "400B"） / chat_items（楼层数）
mes（最后一条正文） / last_mes（mtime 毫秒数）
```

改成 `size / messages / last_text / last` 之后：

```
backup.chats → count 4
  chat_agenttest_20261127-072032.jsonl  size 400B  messages 1  last_text "你好。"  2026-11-26T23:20:32Z
  chat_agenttest_20261127-072042.jsonl  size 534B  messages 1  last_text "你好。"
```

## 四、向量库：记忆检索的底层

酒馆的"向量化记忆"就是 `/api/vector/*`。`collectionId` 通常就是聊天档名，`source` 默认 `transformers`（本地模型），也可以 `openai` / `openrouter` / `cohere` 等（这时要带 `model`）。

| 工具 | 端点 | 说明 |
| --- | --- | --- |
| `vec.list` | `/api/vector/list` | 这个集合索引了多少条（返回 hashes） |
| `vec.query` | `/api/vector/query` | 语义检索：`topK` + `threshold`，回 index / hash / score / 前 160 字 |
| `vec.insert` | `/api/vector/insert` | 写 `{hash, text, index}` 数组，可手动补索引 |
| `vec.purge` | `/api/vector/purge` / `purge-all` | 清集合；全清要 `confirm` |

`score` 会被四舍五入到 3 位，`threshold` 默认 0 不过滤。服务端在索引损坏时会返回 307 重定向去重建——工具会把非 2xx 直接抛成带状态码的错误，能看到 `HTTP 307`。

实测（测试环境没配 embedding 源，走的 transformers 空索引）：

```
vec.list {collectionId:'test'} → ok true, count 0, hashes []
```

这里能"成功但为空"是因为 `list` 只是读已知 hash 表，不触发 embedding；真正 query 才会去加载模型。**所以 vec.list 是一个安全的探针：先看有没有索引，再决定要不要 query。**

## 五、统计

`/api/stats/get` 返回的是按头像聚合的对象，但里面混着 `timestamp` 这种元数据（值是数字）。第一版直接 `Object.entries` 就把 `timestamp` 当成了一个角色。现在按「value 必须是对象」过滤：

```
stats.get → characters 1（不是 2）
  default_Seraphina.png: user_msg_count 0, non_user_msg_count 0, total_swipe_count 0, chat_size 0
```

`stats.recreate` 走 `/api/stats/recreate`，从磁盘聊天文件重建全部统计——数字对不上时用，会遍历所有聊天，慢。

## 六、这一版没做的

- **世界书改名**：JS-Slash-Runner 的 `renameWorldbook` 在源码里是**注释掉的**（`worldbook.ts:416`，`// export function renameWorldbook`），`@types.txt` 里同样是注释。原生 `/api/worldinfo/*` 也没有 rename。要改名只能"读 → 建新本 → 删旧本"，会丢所有绑定，所以没做。
- `backup.chat/download` 是浏览器下载（`response.download`），前端 fetch 拿不到内容，只有 blob，做不成工具。
- `secrets/*`：`/api/secrets/view` 需要 `config.yaml` 里 `allowKeysExposure: true`，默认关闭；`/api/secrets/settings` 只回 `{allowKeysExposure:false}` 这一个布尔。为了不碰密钥，整块跳过。
